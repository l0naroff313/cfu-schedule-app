# ADR 0003: синхронизация личных данных по установочной идентичности

## Статус

Принято.

## Контекст

В приложении нет учётной записи. Заметки и задания должны оставаться доступными офлайн, а их создание, изменение и удаление — безопасно доходить до сервера после восстановления сети. Установочный секрет нельзя хранить на сервере в открытом виде или отправлять без TLS.

## Решение

- Клиент создаёт UUID установки и 256-битный секрет один раз и хранит их в Android Keystore/iOS Keychain.
- `POST /api/v1/installations/register` идемпотентно регистрирует UUID. PostgreSQL хранит только HMAC-SHA-256 секрета с серверным pepper.
- После проверки секрета сервер выдаёт JWT на 15 минут. Идентификатор владельца заметок и заданий берётся только из проверенного `installation_id` claim.
- Каждое локальное изменение получает отдельный `MutationId` и сохраняется в SQLite-очереди до подтверждения API.
- Операции одной записи отправляются строго по порядку через идемпотентные `PUT` и `DELETE` endpoints. Конфликт одной записи не блокирует синхронизацию других заметок и заданий.
- Сервер сохраняет результат каждой мутации в реестре `(InstallationId, MutationId)`. Поэтому повтор уже подтверждённого запроса не изменяет данные второй раз, даже если после него были применены более новые мутации.
- Удаление является tombstone, а не физическим удалением. Это защищает от возврата записи при запоздавшей офлайн-операции.
- Для разных установок используются составные ключи `(InstallationId, EntityId)`, поэтому один UUID записи не позволяет прочитать или изменить чужие данные.
- Синхронизация запускается в фоне после изменения, при старте приложения и при восстановлении доступа в интернет. Без API приложение продолжает работать локально, сохраняя очередь.
- Клиент повторяет временные ошибки сети, `408`, `429` и `5xx` до трёх раз с экспоненциальной задержкой и поддержкой `Retry-After`. Во всех попытках используется исходный `MutationId`.
- URL API принимается только с `https` и задаётся локальным MSBuild-свойством `UniversityScheduleApiBaseUrl`; обход проверки сертификата не используется.

## Разрешение конфликтов

Сервер принимает новую мутацию, если её клиентское время не старше сохранённого. При одинаковом времени решает порядок доставки. Старые мутации возвращают HTTP `409 Conflict`, `Disposition = Conflict` и текущее серверное состояние.

Клиент не удаляет такую операцию: переводит её в состояние `Conflict`, сохраняет код ошибки и JSON серверной версии. Более поздние операции той же записи остаются заблокированы, а другие записи продолжают синхронизироваться. При выборе локальной версии очередь создаёт новый `MutationId` и более новую временную метку; простая повторная отправка старого конфликтного запроса запрещена, потому что сервер воспроизведёт сохранённый результат из реестра мутаций. UI выбора «локальная/серверная версия» будет следующим этапом.

## Ограничения

- Установочная идентичность не является пользовательской учётной записью и не переносит данные между разными устройствами.
- Текущий клиент отправляет локальные изменения на сервер. Полное восстановление локальной базы из серверного snapshot будет отдельным этапом; API чтения и tombstones уже предусмотрены.
